# 描画最適化ベンチマーク

PR「背景テクスチャの毎フレーム再読込を排除し、GPUアクセラレーションを効かせやすくする」で行った
描画最適化のうち、**変更点1〜3**（純粋にCPU/メモリ上の最適化で、GPUやディスプレイに依存しないもの）
のビフォーアフターを定量的に計測するためのベンチマーク一式。

変更点4（`util.ImageUtil`によるGraphicsConfiguration互換化）と変更点5
（`-Dsun.java2d.d3d=true`）は、実際のWindows + GPU + Direct3Dパイプラインに依存する効果であり、
このベンチマーク（どの環境でも同じ条件で測れることを優先し、意図的にディスプレイ・GPUに依存しない
作りにしている）では測れない。これらは別途、実機のWindownsでの確認が必要（後述）。

## 計測対象

| # | 対象 | legacy（最初の修正前の再現） | 中間（1回目の修正の再現） | current（現行実装の再現） |
|---|------|----------------------|------------------------|------------------------|
| 1 | `GamePanel.drawBackground()` | 毎フレーム`ImageIO.read()`でPNGを再読込 + `TexturePaint`で塗る | `current-texturepaint`: 起動時に1回だけ読み込むが、塗りは依然`TexturePaint` | `current-tiled`: `TexturePaint`をやめ、`drawImage()`でタイル状に描く |
| 2 | `GameStage.draw()` のレイヤー振り分け | `RenderLayer`の数だけ全オブジェクトを毎回フルスキャン（**現行実装もこれ。詳細は後述**） | `current`: 1回のスキャンで振り分けるが`ArrayList`を毎回新規確保（不採用） | `current-reused`: バッファを再利用（不採用、後述） |
| 3 | `TeamInfoText` / `RotationChars` | 毎フレーム`GlyphVector`から文字の輪郭を再計算 | - | 表示内容が変わらない限りShapeをキャッシュ |

いずれも、実際の本番コードを直接呼ぶのではなく、各ファイルに「修正前のアルゴリズムを再現した
legacyメソッド」と「修正後のアルゴリズムを再現したcurrentメソッド」を両方実装し、
同一データ・同一条件下で計測して比較している（本番コードが将来変わってもこの比較の土台が
変わらないようにするため、意図的にこうしている）。

## 使い方

### Linux / macOS

```bash
cd benchmark
./run_benchmark.sh                # デフォルト: warmup=200, iterations=2000
./run_benchmark.sh 50 500         # 手早く確認したい場合
```

### Windows

```
cd benchmark
run_benchmark.bat
run_benchmark.bat 50 500
```

どちらもリポジトリのルートに自動で移動してから、`src`配下の本体コードと
`benchmark/src`配下のベンチマークコードをまとめてコンパイルし、実行する。
Windowsでも`benchmark\run_benchmark.bat`をダブルクリックするだけで実行できる
（内部で`cd /d "%~dp0\.."`しているので、どのディレクトリから実行しても動く）。

JDK（`javac`/`java`）がインストールされ、PATHに通っていることが前提。

## 結果の出力先

- `benchmark/results/<timestamp>-<os>.txt`
  その回の実行結果の全文（人間が読む用）。
- `benchmark/results/history.csv`
  実行するたびに1行ずつ追記される、全履歴のCSV。列は
  `timestamp_utc,os,os_name,os_version,os_arch,java_version,git_commit,benchmark,scenario,iterations,mean_ms,median_ms,p95_ms,min_ms,max_ms`。
  **Linuxで測った行とWindowsで測った行が同じファイルに積み重なる**ので、
  `os`列や`os_name`列でフィルタすれば両者を並べて比較できる（Excel/スプレッドシートに読み込むか、
  後でこのCSVをAIに渡して分析させるのでも良い）。

このベンチマーク自体は今後も削除せず、`src/`本体のレンダリングコードを変更したときに
「本当に速くなっているか」を都度確認するために使う想定。

## 数値の読み方

- `mean` / `median` / `p95` / `min` / `max`: ウォームアップ後に計測したN回の実行時間（ミリ秒）の統計値。
  `median`と`p95`の差が大きい場合はGC一時停止やOSスケジューリングの影響で一部の実行が遅くなっていることを示す。
- `speedup (mean)`: `legacyのmean / currentのmean`。1.0xより大きいほど改善、1.0x未満は悪化。

### なぜ`warmup`と`iterations`を大きく保つ必要があるか

変更点2・3は1回あたり数マイクロ秒〜数百マイクロ秒程度ときわめて軽い処理のため、
JIT（JITコンパイラ）が十分に最適化を終えた「定常状態」に達するまでにある程度の実行回数が必要になる。
実際、`warmup=200`程度ではJITの最適化が不十分で、本来の大小関係が逆転して見えることが
検証中に起きた。そのため`LayerBucketBenchmark`と`GlyphCacheBenchmark`は、
`run_benchmark`に渡した値が小さくても内部で最低5000回のウォームアップ・計測を確保するようにしている
（変更点1の背景テクスチャ計測はディスクI/Oを含み1回が遅いため、こちらは渡された値をそのまま使う）。

## 重要な発見: 変更点2（レイヤー振り分け）は実測では悪化している

このベンチマークを作って初めて判明した、やや意外な結果。

ダミーの`GameObject`(draw()はほぼ何もしない)を実際のステージに近い比率(350個)で用意し、
`legacy`(4回フルスキャン) / `current`(1回のスキャンで振り分けるが、`ArrayList`を毎回新規に4つ確保) /
`current-reused`(1回のスキャンで振り分け、`ArrayList`を再利用してclear()だけする)の3つを比較すると:

```
legacy        : mean=0.0015ms
current       : mean=0.0048ms  (legacyの約0.3倍、つまり3倍以上遅い)
current-reused: mean=0.0022ms  (legacyの約0.7倍、まだ少し遅い)
```

つまり、「4回フルスキャンを1回のスキャンに減らす」という変更そのものは、**少なくともこの物量
（オブジェクト350個、draw()がほぼ無コスト）では速くなっておらず、むしろ毎フレームの
`ArrayList`新規確保ぶん遅くなっている**。バッファを再利用する`current-reused`に直すと
かなり改善するが、それでも単純な4回フルスキャンには僅かに届かない。

### ただし実際のゲームでは問題にならない

上記の差はいずれも**1フレームあたり数マイクロ秒**のオーダーで、60FPSのフレーム予算
(16.6ミリ秒)の0.1%にも満たない。実際のゲームでは各オブジェクトの`draw()`自体
（画像のアフィン変換・blit）が1オブジェクトあたりこれより遥かに重いため、
レイヤー振り分けの方式差は実際のフレームタイムには実質的に現れない。

### 追加調査と結論: 元の4回フルスキャン方式に戻した

上記の結果を受けて、「適切なデータ構造は何か」を2方向から調査した。

**(a) ソースコード調査: GameObjectのレイヤーは実際いつ変わるのか**

`src/stage/`以下の各`getRenderLayer()`の実装を全て確認したところ:

| クラス | レイヤーが変わるタイミング | 生涯での変化回数 |
|---|---|---|
| `Wall` | 変わらない | 0回 |
| `Base` | 変わらない（常にDEBRIS扱い） | 0回 |
| `Tank` | 死亡時・リスポーン時 | 試合中に数回（頻度は低い） |
| `Block` | 設置直後(BABY→通常)・破壊時 | 2回 |
| `Bullet` / `Missile` | 着弾・寿命切れ時に1回だけ | 1回（その後まもなく消滅） |

つまり、オブジェクトの大半（壁・基地）は**一切レイヤーが変わらず**、変わるものも
**生涯で1〜2回だけ**という、フレームごとに見ればごく稀なイベントだと分かった。
また`addGameObject()`はGUIスレッド（`GamePanel`）とネットワークスレッド
（`NetworkManager`）の両方から呼ばれており（`ConcurrentHashMap`で保護されている）、
この並行性も踏まえる必要がある。

**(b) 実際のゲームエンジンはどう実装しているか**

サブエージェントに調査を依頼した結果（詳細は本PRの会話ログ参照）:

- Unity（sortingLayer/sortingOrder）やGodot（z_index）のような大規模エンジンは、
  実際に「dirty-flagで変化を検知し、変わった時だけ永続的なバケツ構造に再挿入する」
  方式を内部で採っている。ただしこれは数千〜数万オブジェクト規模を想定した
  エンジン内部の最適化であり、スクリプトレベルのゲームコードで同じ複雑さを
  背負うのは一般的ではない。
- LibGDXなどより軽量なフレームワークでは、むしろ**「毎フレーム`List.sort()`で
  レイヤー順に並べ替える」方式がよく使われる**。TimSort（Javaの`List.sort()`の実装）
  は「ほぼソート済みのデータ」に対してはO(N)に近い速度で動作するため、
  「レイヤーがほとんど変わらない」という今回の調査結果とも相性が良い。
- 350個程度のオブジェクト数では、(a)(b)どちらの観点からも、永続的な差分更新構造
  を自前で実装するのは複雑さに見合わない、という結論になった。

**結論**: `GameStage.java`は、元の「レイヤー数ぶん全オブジェクトを走査する」単純な
4回フルスキャン方式に戻した。理由は次の3点が揃ったため:
1. 実測で3案中最速だった
2. オブジェクトのレイヤーがほとんど変化しないという実態に対して、過剰に複雑な
   差分更新構造を導入する必要性がない（業界の実装パターンとも整合する判断）
3. 複数スレッドからの追加を考えると、永続バケツ構造は並行性のバグを増やすリスクがある

「測ったら最初の直感（1回のスキャンの方が速いはず）と逆の結果が出て、
さらに踏み込んで調べたら、結局シンプルな実装が妥当だった」という過程を、
教訓として記録のためここに残しておく。`benchmark/LayerBucketBenchmark.java`には
不採用になった2案も比較対象として残してあり、今後オブジェクト数が大きく増える
ようなことがあれば、再検討の出発点として使える。

## 変更点1の追加修正: TexturePaint→drawImageによるタイル描画

上記の「背景のTexturePaint自体が重い」という発見を受けて、`GamePanel.drawBackground()`を
`TexturePaint`+`fillRect()`から、キャッシュ済みの画像を`drawImage()`でタイル状に繰り返し描く方式
（`GamePanel.drawTiled()`）に変更した。`drawImage()`は、画像がGraphicsConfiguration互換であれば
GPUによる高速blitが期待できる、Java2Dで最も最適化された操作である一方、`TexturePaint`による塗りは
D3D/OpenGLパイプラインのアクセラレーション対象外で常にソフトウェア処理になる（前述の通り）。

このLinux/ソフトウェアレンダリング環境でも、計測で明確な改善が確認できた:

```
legacy              (毎フレームImageIO.read + TexturePaint): mean=17.1ms
current-texturepaint(キャッシュ済み + TexturePaint)        : mean=15.9ms  (legacy比 1.1倍)
current-tiled       (キャッシュ済み + drawImageでタイル描画)  : mean=6.9ms   (legacy比 2.5倍、texturepaint比 2.3倍)
```

ソフトウェアレンダリングのこの環境でも2倍以上速くなっており、実際のWindows+GPU環境では
`drawImage()`がアクセラレーションされる分、さらに大きな改善が期待できる（要実機確認）。

タイル描画の範囲は`Graphics2D#getClipBounds()`（カメラ変換後の呼び出しなので、画面に実際に
映っているワールド座標系の範囲がそのまま返ってくる）で絞り込んでおり、カメラ変換・ズームを
含めて正しく機能することをSwingの実パネル上で検証済み（`graphics.setTransform()`後に
`getClipBounds()`が正しく逆変換された矩形を返すことを確認した）。

### 計測中に踏んだ罠（記録として残す）

`current-tiled`を最初に計測したとき、`mean=0.0002ms`という物理的にあり得ない数値が出た
（数百KB〜数MBのピクセルコピーが200ナノ秒で終わるはずがない）。原因は、ベンチマークの
`BufferedImage.createGraphics()`で作った`Graphics2D`は、**明示的にクリップを設定しない限り
`getClipBounds()`が`null`を返す**ため、`drawTiled()`内の`if (area == null) return;`に
毎回引っかかって実質何も描いていなかったこと。実際のSwingの`paintComponent(Graphics g)`では
コンポーネントの描画範囲が自動的にクリップとして設定される（これも実際に検証済み）ため、
本番コード自体に問題はなかったが、ベンチマーク側で`g.setClip(0, 0, width, height)`を
明示的に呼ぶ修正が必要だった。「数値が速すぎる・遅すぎる場合はまず自分のベンチマークコードを疑う」
という教訓として記録しておく。

## 変更点4・5（GPU活用）を実機(Windows)で確認する際のヒント

このベンチマークの対象外だが、将来Windows実機で確認する際のメモ:

- **変更点4**（`util.ImageUtil`によるGraphicsConfiguration互換化）: Java2Dの描画パイプラインの
  トレースログ（`-Dsun.java2d.trace=log` 等）で、画像がアクセラレーションされたサーフェスとして
  扱われているかを確認する方法がある。
- **変更点5**（`-Dsun.java2d.d3d=true`）: Direct3Dパイプラインが実際に初期化されているかどうかは
  起動時のログやトレースで確認できる。D3Dが環境依存で無効化されGDI（ソフトウェア）に
  フォールバックしていないかを見るのが目的。
- **drawImageタイル描画**: 上記の通りこのLinux環境でも2倍以上速くなっているが、実際にGPUの
  blitが使われているかどうかは、やはり`-Dsun.java2d.trace=log`系のトレースで確認するのが確実。
- いずれも**実際のGPU・ドライバに依存する**ため、仮想ディスプレイ（Xvfbなど）や
  GPUなしの環境では意味のある比較ができない。必ず実際のWindows PC（できれば対戦時に
  使う想定の環境に近いGPU）で確認すること。
