# 描画最適化ベンチマーク

PR「背景テクスチャの毎フレーム再読込を排除し、GPUアクセラレーションを効かせやすくする」で行った
描画最適化のうち、**変更点1〜3**（純粋にCPU/メモリ上の最適化で、GPUやディスプレイに依存しないもの）
のビフォーアフターを定量的に計測するためのベンチマーク一式。

変更点4（`util.ImageUtil`によるGraphicsConfiguration互換化）と変更点5
（`-Dsun.java2d.d3d=true`）は、実際のWindows + GPU + Direct3Dパイプラインに依存する効果であり、
このベンチマーク（どの環境でも同じ条件で測れることを優先し、意図的にディスプレイ・GPUに依存しない
作りにしている）では測れない。これらは別途、実機のWindownsでの確認が必要（後述）。

## 計測対象

| # | 対象 | legacy（修正前の再現） | current（修正後の再現） |
|---|------|----------------------|------------------------|
| 1 | `GamePanel.drawBackground()` | 毎フレーム`ImageIO.read()`でPNGを再読込 | 起動時に1回だけ読み込み、参照を再利用 |
| 2 | `GameStage.draw()` のレイヤー振り分け | `RenderLayer`の数だけ全オブジェクトを毎回フルスキャン | 1回のスキャンでレイヤーごとに振り分け |
| 3 | `TeamInfoText` / `RotationChars` | 毎フレーム`GlyphVector`から文字の輪郭を再計算 | 表示内容が変わらない限りShapeをキャッシュ |

いずれも、実際の本番コードを直接呼ぶのではなく、各ファイルに「修正前のアルゴリズムを再現した
legacyメソッド」と「修正後のアルゴリズムを再現したcurrentメソッド」を両方実装し、
同一データ・同一条件下で計測して比較している（本番コードが将来変わってもこの比較の土台が
変わらないようにするため、意図的にこうしている）。

## 使い方

### Linux / macOS

```bash
cd benchmark
./run_benchmark.sh                # デフォルト: warmup=200, iterations=2000
./run_benchmark.sh 50 500         # 手早く確認したい場合
```

### Windows

```
cd benchmark
run_benchmark.bat
run_benchmark.bat 50 500
```

どちらもリポジトリのルートに自動で移動してから、`src`配下の本体コードと
`benchmark/src`配下のベンチマークコードをまとめてコンパイルし、実行する。
Windowsでも`benchmark\run_benchmark.bat`をダブルクリックするだけで実行できる
（内部で`cd /d "%~dp0\.."`しているので、どのディレクトリから実行しても動く）。

JDK（`javac`/`java`）がインストールされ、PATHに通っていることが前提。

## 結果の出力先

- `benchmark/results/<timestamp>-<os>.txt`
  その回の実行結果の全文（人間が読む用）。
- `benchmark/results/history.csv`
  実行するたびに1行ずつ追記される、全履歴のCSV。列は
  `timestamp_utc,os,os_name,os_version,os_arch,java_version,git_commit,benchmark,scenario,iterations,mean_ms,median_ms,p95_ms,min_ms,max_ms`。
  **Linuxで測った行とWindowsで測った行が同じファイルに積み重なる**ので、
  `os`列や`os_name`列でフィルタすれば両者を並べて比較できる（Excel/スプレッドシートに読み込むか、
  後でこのCSVをAIに渡して分析させるのでも良い）。

このベンチマーク自体は今後も削除せず、`src/`本体のレンダリングコードを変更したときに
「本当に速くなっているか」を都度確認するために使う想定。

## 数値の読み方

- `mean` / `median` / `p95` / `min` / `max`: ウォームアップ後に計測したN回の実行時間（ミリ秒）の統計値。
  `median`と`p95`の差が大きい場合はGC一時停止やOSスケジューリングの影響で一部の実行が遅くなっていることを示す。
- `speedup (mean)`: `legacyのmean / currentのmean`。1.0xより大きいほど改善、1.0x未満は悪化。

### なぜ`warmup`と`iterations`を大きく保つ必要があるか

変更点2・3は1回あたり数マイクロ秒〜数百マイクロ秒程度ときわめて軽い処理のため、
JIT（JITコンパイラ）が十分に最適化を終えた「定常状態」に達するまでにある程度の実行回数が必要になる。
実際、`warmup=200`程度ではJITの最適化が不十分で、本来の大小関係が逆転して見えることが
検証中に起きた。そのため`LayerBucketBenchmark`と`GlyphCacheBenchmark`は、
`run_benchmark`に渡した値が小さくても内部で最低5000回のウォームアップ・計測を確保するようにしている
（変更点1の背景テクスチャ計測はディスクI/Oを含み1回が遅いため、こちらは渡された値をそのまま使う）。

## 重要な発見: 変更点2（レイヤー振り分け）は実測では悪化している

このベンチマークを作って初めて判明した、やや意外な結果。

ダミーの`GameObject`(draw()はほぼ何もしない)を実際のステージに近い比率(350個)で用意し、
`legacy`(4回フルスキャン) / `current`(1回のスキャンで振り分けるが、`ArrayList`を毎回新規に4つ確保) /
`current-reused`(1回のスキャンで振り分け、`ArrayList`を再利用してclear()だけする)の3つを比較すると:

```
legacy        : mean=0.0015ms
current       : mean=0.0048ms  (legacyの約0.3倍、つまり3倍以上遅い)
current-reused: mean=0.0022ms  (legacyの約0.7倍、まだ少し遅い)
```

つまり、「4回フルスキャンを1回のスキャンに減らす」という変更そのものは、**少なくともこの物量
（オブジェクト350個、draw()がほぼ無コスト）では速くなっておらず、むしろ毎フレームの
`ArrayList`新規確保ぶん遅くなっている**。バッファを再利用する`current-reused`に直すと
かなり改善するが、それでも単純な4回フルスキャンには僅かに届かない。

### ただし実際のゲームでは問題にならない

上記の差はいずれも**1フレームあたり数マイクロ秒**のオーダーで、60FPSのフレーム予算
(16.6ミリ秒)の0.1%にも満たない。実際のゲームでは各オブジェクトの`draw()`自体
（画像のアフィン変換・blit）が1オブジェクトあたりこれより遥かに重いため、
レイヤー振り分けの方式差は実際のフレームタイムには実質的に現れない。

### 今後の対応について

この結果を踏まえ、`GameStage.java`の現行実装（`current`、毎フレーム4つの`ArrayList`を新規確保）
をどうするかは要検討:
1. そのまま残す（実害は無視できるレベルなので、コードの読みやすさを優先）
2. `current-reused`方式（バッファを`GameStage`のフィールドとして持ち、`clear()`して再利用）に直す
3. 元の4回フルスキャン方式に戻す（このオブジェクト数の範囲では実測で最速だったため）

いずれを選んでも実際のゲームプレイに体感できる差は出ないはずだが、
「測ったら想定と違っていた」実例として記録のためここに残しておく。

## 変更点4・5（GPU活用）を実機(Windows)で確認する際のヒント

このベンチマークの対象外だが、将来Windows実機で確認する際のメモ:

- **変更点4**（`util.ImageUtil`によるGraphicsConfiguration互換化）: Java2Dの描画パイプラインの
  トレースログ（`-Dsun.java2d.trace=log` 等）で、画像がアクセラレーションされたサーフェスとして
  扱われているかを確認する方法がある。
- **変更点5**（`-Dsun.java2d.d3d=true`）: Direct3Dパイプラインが実際に初期化されているかどうかは
  起動時のログやトレースで確認できる。D3Dが環境依存で無効化されGDI（ソフトウェア）に
  フォールバックしていないかを見るのが目的。
- どちらも**実際のGPU・ドライバに依存する**ため、仮想ディスプレイ（Xvfbなど）や
  GPUなしの環境では意味のある比較ができない。必ず実際のWindows PC（できれば対戦時に
  使う想定の環境に近いGPU）で確認すること。
- また、変更点1のベンチマーク結果を見ると、背景のTexturePaint自体のfillRectが
  （このLinux/ソフトウェアレンダリング環境では）1回あたり16〜19ミリ秒と、
  60FPSのフレーム予算をほぼ使い切ってしまうほど重いことが分かった。
  TexturePaintによる塗りつぶしはJava2DのD3D/OpenGLパイプラインでも基本的に
  アクセラレーションされない（CPU側のタイル処理にフォールバックする）ことが知られているため、
  **実機でも同様に重い可能性がある**。もし実機でも背景描画が重いままなら、
  TexturePaintではなく、背景を1枚の合成済み画像として事前に焼き込んでおき、
  `drawImage()`（これはアクセラレーションされる）で済ませる方式への変更を検討する価値がある。
